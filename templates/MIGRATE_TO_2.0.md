# Миграция существующего проекта на R2Team 2.0

Используй [Setup.md](Setup.md), режим migrate. Источник — полный пакет 2.0 с проверенным commit SHA/manifest, не один промпт. Переход с 1.10, 1.20 либо MVP без протокола требует согласованного diff. Сам продукт не переписывается.

## 1. Read-only preflight

Подтверди repo/root/remote/default branch/worktrees, текущий протокол/AGENTS, активных писателей, роли и привязку к людям, TASK/Issue/Work Items/PR, незапушенное/незакоммиченное, OpenSpec/schema/changes и docs. Не запрашивай всю историю чатов. Пользовательские глобальные инструкции имеют приоритет и не отменяются новым локальным файлом.

Сохрани точные refs и ограничения; при негитованном корне оргфайлов сначала согласуй каноническое размещение. Для TFS/CMMI проверь серверные types/fields/states/Parent–Child/Development по [профилю](SETUP-TFS-CMMI.md). Не делай init/update OpenSpec в preflight.

## 2. Выбор и разрешённый diff

По умолчанию переносится активная очередь. Покажи mapping старых ролей в participants/executors/functions, сохраняемые чаты, права, целевые файлы, остатки задач и безопасные точки переключения. Исторические MSG/REPORT остаются историей; существенные текущие факты переносятся в TASK/spec с provenance.

Если пользователь явно разрешил начать организационную очередь заново, сохрани важные решения/незавершённый код/spec/docs и пометь прежнюю очередь неактивной, не DONE. Это не разрешает удалять рабочие файлы. Физическое удаление — отдельный точный список и подтверждение с recoverable history.

Защищены: заполненная спецификация, вся openspec/ включая changes/**/tasks.md и checkboxes, код, docs, ветки/PR, индивидуальные ограничения ролей. Организационные Tasks не равны OpenSpec tasks.md. Пустые шаблоны не копируются поверх заполненного.

## 3. Применение после согласования

Дождись согласованного checkpoint затронутых исполнителей. В отдельной безопасной ветке/worktree внеси минимальный diff AGENTS/TEAM/protocol/Setup/ROLE/SKILLS/COMMANDS. Зафиксируй protocol_version: "2.0", integration_revision и проверенный источник.

Существующие полезные TASK/Issue/Work Item/PR сохраняют идентичность. Уточни owner_executor_id, active_role, контракт/revision, candidate SHA, открытые вопросы, evidence и next_action. Один публикующий владелец на task-ветку.

Сохрани PM; COO может быть его внутренним read-only помощником или явно настроенным самостоятельным исполнителем. Не переноси прежние полномочия автоматически. Heartbeat выключен по умолчанию; текущие scoped automations изменяются лишь по согласованному плану. Чужие projectless расписания не трогаются.

## 4. OpenSpec и skills

Если OpenSpec уже есть — сохраняй структуру/config/metadata и активные changes; не выполняй init/archive ради версии протокола. Нужное изменение артефактов проходит их собственный update/verify/sync workflow.

Если OpenSpec отсутствует — согласуй инструменты и init, составь краткую карту текущих capabilities/источников/gaps. Ближайшая реальная фича проходит explore → propose → approval → apply → verify/tests → sync/docs → archive полного scope. Документирование существующего MVP может быть отдельной ограниченной baseline-задачей; UNKNOWN остаётся явным.

На каждой машине отдельно проверить установленный R2Team и применимые OpenSpec/Superpowers. Не обновлять зависимости до latest без решения. Заполненные specs не означают доказанную полноту.

## 5. Переключение существующих чатов

Для каждой активной задачи записать: завершить по прежнему протоколу либо перевести после checkpoint и принятия новых правил. До cutover 1.10 сохраняет обязательные MSG/reply/notification по своим действующим инструкциям.

Каждый сохраняемый чат читает новый контракт, выполняет cross-check, сообщает обязанности/права, ограничения и готовность. PM фиксирует фактическое принятие в организационном TASK. Изменение файла или успешный send не доказывает принятие. Недоступный чат не считать мигрированным; новый не создавать вместо него без разрешения.

## 6. Проверка и продолжение

Audit источников, прав, mapping, сохранности protected files, согласованности Git/tracker и восстановимости. Опубликовать согласованный commit, проверить remote SHA и доступ получателей. Провести один разрешённый малый workflow; непроверенные API/runtime/wake части отметить NOT_RUN.

Итог: source SHA, применённый diff, сохранённые ограничения, статус каждого чата, какие TASK ещё на старой версии, ближайший next_action. При откате процесса — отдельное согласованное обратное изменение, не git reset и не потеря продуктовой работы.
